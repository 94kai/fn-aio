# Lucky 统一业务入口

## 目标与边界

```text
管理：飞牛 1023/1024 → 已登录 /app/aio/ → AIO 私有 Unix Socket
业务：Lucky HTTPS 1025 → AIO 回环 HTTP 19090 → /服务标识/ → 本机业务
```

1023/1024 是当前用户的飞牛端口，不是程序内置默认值。19090 为建议的内部端口，不是强制值；1025 由 Lucky 监听，AIO 不负责证书或公网监听。Lucky 的安装、配置和重载由用户完成。本功能不会修改飞牛 Nginx、Lucky、Docker、路由器或业务容器。

管理入口始终要求指定飞牛管理员，业务入口只做业务转发，不能列出或修改服务。外部业务不经过飞牛登录，必须依靠业务自身鉴权。所有现有服务缺省 `publicAccess:false`，不会因升级自动公开。

## 策略

在本机网关策略的顶层添加（下面不是完整 JSON）：

```json
"publicProxy": {
  "listenHost": "127.0.0.1",
  "port": 19090,
  "origin": "https://your-nas.example:1025"
}
```

- `listenHost`：仅允许 `127.0.0.1` 或 `::1`；不允许 `0.0.0.0`、局域网 IP 或公网 IP。回源示例使用 IPv4，若选择 IPv6，Lucky 上游应为 `http://[::1]:19090`。
- `port`：1024～65535，排除飞牛默认 5666/5667，并与外部端口不同。请先确认未占用。
- `origin`：固定外部 HTTPS Origin，不含路径、尾斜杠、查询、账号密码或通配符；不能与任何飞牛管理 `allowedOrigins` 相同。它用于恢复可信的对外协议、Host、短路径链接和安全 Cookie。
- 缺少整个 `publicProxy` 字段：完全不启动业务 TCP 监听。不能用 null 或半份配置表示停用。
- 当前服务回源端口禁止指向该内部端口及该外部端口，以减少直接转发循环；不要将 Lucky 或飞牛入口配置为业务后端。策略不应包含任何密码或令牌。

先备份私人配置，再将相同变更同步到本机构建策略与生产策略；使用正式 FPK 和应用中心升级，不直接覆盖已安装代码。路径、校验、备份及升级风险参见[配置手册](<configuration.md>)。修改策略后需重启 AIO；修改服务列表无需重启。

启动时先绑定业务端口，再创建管理 Socket；端口占用会拒绝整个 AIO 启动，避免应用中心误判为已就绪。升级前请检查端口，失败时移除业务策略并重新启动可恢复原有私有模式，不要关闭管理鉴权。

## Lucky 由用户配置

| 项目 | 值 |
| --- | --- |
| 对外监听 | HTTPS，1025 |
| 对外域名 | 你的域名，必须匹配策略的 origin |
| 证书 | 由 Lucky 管理，客户端必须信任 |
| 路径匹配 | 所有路径；不要逐服务配置 |
| 后端 | `http://127.0.0.1:19090` |
| 路径重写 | 不重写、不删除任何路径前缀 |
| 回源 Host | 保留外部 Host，含 `:1025`；不要使用后端 IP 或 localhost |
| WebSocket | 启用升级转发 |
| 正文处理 | 不替换 HTML/JavaScript；按需调整上传限制和超时 |

Lucky 只承担 HTTPS 入口，不转回飞牛的 1023/1024，也不向 AIO 注入飞牛身份或密码。AIO 使用策略固定的外部 Origin，不信任客户端提供的 Forwarded 和飞牛身份；认证所需的业务 Authorization 正常转发。

**容器注意**：Lucky 若在普通 bridge 网络容器内，`127.0.0.1` 是容器自己，不是 NAS。此版本仅支持回环业务监听，需 Lucky 已使用 host 网络等方式能访问宿主回环；不能仅改为 NAS 局域网 IP 来放开 AIO。若当前部署不满足，应先评估网络方案，AIO 不自动修改 Lucky 网络。

## AIO 中操作

1. 正常登录飞牛，进入 `/app/aio/`。
2. 编辑目标服务，确认本机地址、HTTP 端口和基础路径正确。
3. 勾选“允许通过 Lucky 外部入口访问”，确认业务自身有登录保护。
4. 保存后卡片显示外部链接。新开启或重新启用对外服务需二次确认，导入配置也适用。
5. 外部服务链接为 `https://your-nas.example:1025/服务标识/`，使用标识而不是显示名称。

路由示例：

```text
/vaultwarden/identity/connect/token
  → 基础路径为 / 时：/identity/connect/token

/notes/page?q=1
  → 基础路径为 /base 时：/base/page?q=1
```

`/notes` 自动 308 到 `/notes/`，保留查询参数。根路径和未匹配服务返回 404，无公共首页。未显式开放、停用、撤销开放或删除服务后，新请求均返回 404；不主动切断已有连接。私有访问 `/app/aio/s/notes/` 不受外部开关影响，但始终要求飞牛身份。

业务监听器没有管理页、管理 API 或管理静态资源。未知路径不会回退到管理入口；即使携带伪造飞牛管理员 Header 也不能获得管理权限。如果服务标识本身叫 app 或 api，相应路径也只可能进入该业务后端，不会访问 AIO 的管理路由。

## Cookie、来源与兼容性

- 外部 Cookie 名称增加独立前缀 `aio_public_服务标识__`，响应移除 Domain 并限定 Path 为业务短路径，HTTPS 下添加 Secure；回源只接收该服务、该入口前缀的 Cookie，再恢复原名。不会向后端传飞牛 Cookie、私有入口或其他服务的前缀 Cookie。
- 浏览器 Cookie 不按端口隔离。因此不能在同一域名上简单透传全部 Cookie。私有与外部入口不共享业务登录，需分别登录。JavaScript 必须读取固定 Cookie 名的应用仍可能不兼容。
- 请求 Host 必须匹配策略的外部 Host 和端口。携带 Origin 时必须是固定外部 Origin；拒绝跨站业务请求，仅允许有限的跨站首页文档导航。不自动放开 CORS；携带扩展 Origin 的客户端需另行核对，不能宣称所有客户端均兼容。
- 支持 HTTP、业务 Authorization、WebSocket、Range 和流式传输。提供短路径 X-Forwarded-Prefix，改写匹配回源主机的常见 Location，避免重复追加已存在的挂载前缀。
- 不替换 HTML/JavaScript，写死 `/api`、`/assets` 等根路径的应用仍需配置自己的子路径。OAuth、Service Worker、固定 Cookie 名及下载重定向需逐个验证。
- 同一外部 Origin 下所有业务页面仍互相信任；路径与 Cookie 前缀不是恶意服务隔离。外部业务端口必须与管理 Origin 分开，但同一域名下不同端口仍然共享 Cookie 的域名范围。不要开放不可信服务。
- 回环监听不区分本机进程身份：本机其他进程也可以连接；NAS 上的恶意本地用户不在隔离边界内。公网防护、限速和 TLS 由前置反代负责。

## Vaultwarden / Bitwarden

外部地址例如 `https://your-nas.example:1025/vaultwarden/`。Vaultwarden 的 DOMAIN 应配置为对应子路径地址，例如：

```text
DOMAIN=https://your-nas.example:1025/vaultwarden
```

基础路径填写后端真实提供的路径，不是照抄外部挂载路径；需结合现有 Vaultwarden 部署核对。Bitwarden 客户端使用该外部地址，而非飞牛私有入口。后端配置和容器重启由用户另行处理。

本功能去掉的是飞牛前置会话要求，不保证 Bitwarden 的所有平台/版本都已验收。须验证配置发现、登录、同步、附件和通知；如出现错误，检查实际状态码、请求路径与响应类型，不记录令牌或正文，不凭“网页能打开”判定客户端成功。

## 验收建议

- AIO：先执行 `npm run verify`，再以本机策略构建正式 FPK；测试通过不代表安装成功。
- 安装：通过飞牛应用中心升级并确认版本 0.2.0；先备份，不使用会卸载清数据的 install-local。
- Lucky：检查本机入口可达、Host 保留和路径原样转发，再验证真实 HTTPS 证书和外网连接。
- 安全：未授权服务返回 404，业务入口不能读取服务列表或管理资源；原管理入口匿名访问仍被拦截。
- 客户端：由用户在真实浏览器和 Bitwarden 上验收。本次开发不主动运行浏览器，不代表已有生产或客户端验证结果。
